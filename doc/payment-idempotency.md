# 付款 Idempotency 設計筆記

這份文件記錄付款流程之後必須補強的 idempotency 設計。

## 1. 為什麼需要

Idempotency 的目的，是讓同一個會產生副作用的請求被重送時，後端只執行一次，並且回傳一致的結果。

在付款流程裡，副作用包含：

- 建立訂單
- 建立付款紀錄
- 呼叫外部支付服務
- 將 order 標記為 paid
- 將 reservation 標記為 confirmed
- 扣除或確認庫存

如果沒有 idempotency，前端 retry、後端 retry、支付 provider callback 重送、circuit breaker fallback，都可能造成狀態不一致或重複付款。

付款系統最重要的目標：

- 不重複建立訂單
- 不重複建立同一筆 provider transaction 的 payment
- 不重複把同一張 order 標記為 paid
- 不讓使用者被重複扣款
- 同一個請求 retry 時，可以回傳第一次處理的結果

## 2. 只靠 order status 不夠

`order.status` 是必要的狀態機防線，但不是完整的 idempotency。

`order.status` 可以擋住「order 已經 paid 之後，又有人想再付款」這種情況。

但是它無法完整處理以下風險。

### 2.1 第一次付款成功，但 response timeout

流程：

1. 前端送出 `POST /payments`。
2. 後端建立 payment，並把 order 改成 paid。
3. 後端回 response 時，網路 timeout 或前端沒有收到 response。
4. 前端不知道付款是否成功，因此重送同一個 `POST /payments`。
5. 後端看到 `order.status = paid`，可以知道不能再付一次。

問題是：前端拿不到第一次成功的 payment response。

如果只靠 `order.status`，後端可能只能回：

```json
{
  "error": "order cannot be paid"
}
```

但對使用者來說，實際上付款已成功，畫面卻顯示錯誤，體驗和狀態都不清楚。

完整 idempotency 應該回傳第一次成功的結果：

```json
{
  "payment_no": "PAY-xxx",
  "status": "paid"
}
```

### 2.2 兩個 request 同時進來

流程：

1. 使用者連點兩次付款，或瀏覽器/前端重送。
2. Request A 讀到 `order.status = pending_payment`。
3. Request B 也讀到 `order.status = pending_payment`。
4. A 開始呼叫 payment provider。
5. B 也開始呼叫 payment provider。

問題是：兩個 request 可能都在 order 還沒被改成 paid 前通過狀態檢查。

只靠 `order.status`，必須搭配 transaction lock、唯一約束、payment attempt 或 idempotency key，才能避免同一筆 order 同時觸發多次付款流程。

### 2.3 外部支付服務 timeout，但其實可能成功

流程：

1. 後端呼叫 primary payment provider。
2. 本地端等待 provider response 時 timeout。
3. 後端不知道 primary provider 是否已收到並接受付款請求。
4. Circuit breaker 或 fallback 機制把請求改送 backup provider。
5. primary provider 之後 callback 成功。
6. backup provider 也可能 callback 成功。

問題是：如果沒有 payment attempt 與 idempotency 設計，可能發生 primary 和 backup 都完成付款。

這是接入 circuit breaker / fallback provider 時最需要注意的風險。

原則：

- timeout 不等於付款失敗。
- 不可以在不確認 primary attempt 已失敗或已過期前，直接讓 backup provider 對同一筆 order 收款。
- fallback 如果被允許，必須建立新的 payment attempt，並清楚記錄 provider、attempt 狀態與關聯。

## 3. 目前專案狀態

目前專案有局部防重複，並已先補上 payment-only idempotency 的基礎，但還不是完整付款 provider idempotency。

已有防線：

- `orders.order_no` 有 unique index。
- `orders.reservation_id` 有 unique index。
- `payments.payment_no` 有 unique index。
- ECPay callback 會檢查 `TradeNo` 是否已存在。
- ECPay callback 看到 order 已 paid 會直接 return。
- `idempotency_keys` table 已建立。
- `POST /payments` 已支援 `Idempotency-Key` header。
- `POST /payments` 會保存第一次成功的 payment response，讓同 key、同 body retry 可以 replay。

仍缺少：

- `Idempotency-Key` 目前是過渡期 optional，尚未對前端強制。
- `POST /orders` 雖然有 DB unique 保護，但 retry 時不一定能拿回第一次建立的 order response。
- 尚未建立正式 `payment_attempts`。
- 尚未接 payment provider start flow。
- 尚未處理 provider timeout 後 fallback 的完整 attempt 狀態。
- `POST /queue/join` 有 `request_id`，但目前不是完整 idempotency layer。

## 4. 未來設計

之後應該增加共用的 idempotency layer，用在會產生副作用的 API。

建議優先保護：

- `POST /orders`
- `POST /payments`
- 未來的 `POST /payments/start`
- payment provider callback processing

可選擇性保護：

- `POST /queue/join`
- `POST /reservations`

建議 request contract：

```http
Idempotency-Key: 018f0f58-8f62-7f5e-9f28-0c2a1b9c4e77
```

建議 table：

```sql
CREATE TABLE idempotency_keys (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    key VARCHAR(255) NOT NULL,
    user_id BIGINT NULL,
    endpoint VARCHAR(100) NOT NULL,
    request_hash VARCHAR(128) NOT NULL,
    status SMALLINT NOT NULL,
    response_status INTEGER NULL,
    response_body JSONB NULL,
    locked_until TIMESTAMPTZ NULL,
    expires_at TIMESTAMPTZ NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE UNIQUE INDEX idx_idempotency_keys_key_endpoint
ON idempotency_keys (key, endpoint);
```

建議行為：

1. Client 對 side-effecting request 傳入 `Idempotency-Key`。
2. Backend 根據 route、user、request body 算出穩定的 request hash。
3. 如果 key 不存在，建立一筆 idempotency record，狀態設為 processing。
4. 執行真正的業務邏輯。
5. 成功或失敗後，保存 response status 和 response body。
6. 如果同 key、同 request hash 再送一次，直接回第一次保存的 response。
7. 如果同 key、不同 request hash 再送一次，回 idempotency conflict。
8. 過期的 key 可由背景 job 清理，例如 TTL 24 小時。

## 5. Payment Provider 與 Circuit Breaker 注意事項

未來接 payment provider 和 circuit breaker fallback 時，idempotency 會變得更重要。

必要保護：

- 每個 idempotency key 只能產生一個內部 payment attempt。
- 發給 provider 的 merchant trade number 必須唯一且可追蹤。
- 必須保存 provider name、provider trade number、request payload hash、callback payload。
- callback 必須用 provider transaction number 做防重複。
- primary provider timeout 時，不可以直接假設付款失敗。
- 如果 fallback 到 backup provider，必須建立新的 payment attempt，並記錄原 attempt 和 fallback attempt 的關係。

建議流程：

1. `POST /payments/start` 建立 `payment_attempt`。
2. 後端透過 provider router 選擇 payment provider。
3. Circuit breaker 判斷 primary provider 是否可用。
4. 後端用穩定的 merchant trade number 呼叫 provider。
5. Provider callback 回來後驗簽。
6. Callback handler 做 idempotency 檢查。
7. 後端只執行一次：payment paid、order paid、reservation confirmed。

## 6. 驗收條件

- 同一個 `POST /orders` 使用相同 idempotency key 重送時，回同一份 order response。
- 同一個 `POST /payments` 或 `POST /payments/start` 使用相同 idempotency key 重送時，回同一份 payment response。
- 同一個 idempotency key 如果搭配不同 request body，必須回錯誤。
- 同一個 provider callback 重送時，不會建立第二筆 payment。
- 已 paid 的 order 不會被再次付款。
- 測試要涵蓋 frontend retry、雙 request 並發、provider callback 重送、provider timeout 後 fallback 的情境。

## 7. Phase 1：Payment-only idempotency

第一階段先只套用在付款 API，不擴散到所有副作用 API。

範圍：

- `POST /payments`
- 未來的 `POST /payments/start`
- payment provider callback

目前後端已先支援 `POST /payments` 的 `Idempotency-Key` header。

目前是過渡期設計：

- 前端尚未改動，所以 header 暫時不強制。
- 如果前端有送 `Idempotency-Key`，後端會啟用 payment idempotency。
- 如果前端沒有送 `Idempotency-Key`，後端維持原本付款流程。
- 文件先要求前端後續要遵守，避免接 payment provider 後才補造成風險。

`POST /payments` request 範例：

```http
POST /payments
Idempotency-Key: 018f0f58-8f62-7f5e-9f28-0c2a1b9c4e77
Content-Type: application/json
```

```json
{
  "order_id": 1,
  "method": "credit_card"
}
```

後端行為：

1. 如果沒有 `Idempotency-Key`，照原本短期付款流程處理。
2. 如果有 `Idempotency-Key`，後端用 `key + endpoint` 查詢 `idempotency_keys`。
3. 如果 key 不存在，建立 processing record。
4. 後端執行 payment。
5. payment 成功後，保存 response status 和 response body。
6. 同 key、同 request body retry 時，直接回第一次保存的 payment response。
7. 同 key、不同 request body retry 時，回 conflict。
8. 同 key 還在 processing 時，回 conflict，避免同一筆付款同時執行。

Phase 1 table：

```sql
CREATE TABLE idempotency_keys (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    key VARCHAR(255) NOT NULL,
    user_id BIGINT NULL,
    endpoint VARCHAR(100) NOT NULL,
    request_hash VARCHAR(128) NOT NULL,
    status SMALLINT NOT NULL,
    response_status INTEGER NULL,
    response_body JSONB NULL,
    locked_until TIMESTAMPTZ NULL,
    expires_at TIMESTAMPTZ NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE UNIQUE INDEX idx_idempotency_keys_key_endpoint
ON idempotency_keys (key, endpoint);

CREATE INDEX idx_idempotency_keys_expires_at
ON idempotency_keys (expires_at);
```
